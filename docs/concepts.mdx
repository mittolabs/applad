A handful of ideas run through every part of Applad. Learn these once and the
rest of the docs read easily.

## Organizations and projects

A **project** is an isolated backend: its own database, users, files, functions,
and API keys. Nothing in one project can see anything in another.

A project always belongs to an **organization**. An organization is a group of
people (your team) that owns projects and billing. You create an organization
first, then create projects inside it. A project can never exist without one.

## Users vs. operators

Two different kinds of identity, and it is worth keeping them straight:

- **App users** are the people who use the app you build. They live inside a
  project, sign in with [authentication](/build/authentication), and are subject to
  [permissions](/build/permissions). Your app creates and manages them.
- **Console users** are you and your teammates, the operators who administer the
  instance through the admin console. They belong to organizations, not to a
  single project.

## Sessions and API keys

There are two ways to authenticate a request, and they mean very different things:

- A **session** identifies an app user. It is created at sign-in and carried as a
  bearer token. A request with a session acts as that user, and permissions
  decide what it can do. This is what [client SDKs](/sdks) use.
- An **API key** is a project-scoped secret for trusted server-side code. A
  request with an API key has full access and bypasses user permissions. This is
  what [server SDKs](/sdks) use. Never ship an API key in a client app.

## Permissions and roles

Access to data is decided by [permissions](/build/permissions): short strings like
`read("team:abc")` attached to a table or an individual row. A request carries
**roles** derived from the caller's identity (`any`, `users`, `user:<id>`, and
the [teams](/build/teams) they belong to as `team:<id>`), and access is granted when a
permission matches one of those roles. Roles are always resolved on the server
from who the caller actually is, never from anything the client sends.

Enforcement is real PostgreSQL row-level security, so a row a caller may not read
is simply invisible to them, in the query builder and in raw SQL alike.

## Content mode (optional)

Any [databases](/build/databases) table can be turned into an editorial collection
instead of a plain data table, so content and application data share one engine
and one API. A content-mode table gains a draft and published workflow, a slug
and locale for translations, and a version snapshot on every write, while the
rows API stays the same with a few editorial additions:

```bash
# only published English entries
GET  /v1/databases/{db}/tables/{table}/rows?status=published&locale=en

POST /v1/databases/{db}/tables/{table}/rows/{row}/publish
GET  /v1/databases/{db}/tables/{table}/rows/{row}/versions
```

Turning content mode off only hides the editorial tools. Nothing is deleted.
