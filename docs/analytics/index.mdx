Analytics is first-party event tracking: your app records **events** ("signed
up", "added to cart"), and Applad counts them, breaks them down over time, and
computes daily active users and conversion **funnels**. It lives under
`/v1/analytics`, in the same project as your data, so you are not shipping
product usage to a third party.

The same section also carries what the platform measures about itself — request
latency, uptime monitors and cron check-ins — because a self-hosted install
should not need a second product to learn whether its own scheduled job ran.
Application diagnostics (errors, logs, session replays) are deliberately not
here: that is [Bugslad](https://bugslad.com), a separate product.

| Capability | What it does | Routes |
|---|---|---|
| Events | Record what people do in your app, then read the stream back or roll it up | `GET/POST /analytics/events`, `/events/batch`, `/events/counts` |
| Active users | Distinct users per day over a window, and a five-minute live snapshot | `GET /analytics/dau`, `GET /analytics/realtime` |
| [Funnels](/analytics/funnels) | Ordered event sequences with per-step conversion | `GET/POST/DELETE /analytics/funnels` |
| [Performance](/analytics/performance) | Per-route latency percentiles Applad samples on every request | `GET/POST /analytics/performance` |
| [Uptime](/analytics/uptime) | Applad polls a URL on a schedule and records status, latency and uptime | `GET/POST/DELETE /analytics/uptime` |
| [Crons](/analytics/crons) | Scheduled jobs check in when they run; the monitor keeps the history | `GET/POST/DELETE /analytics/crons`, `.../{monitorId}/checkin` |
| Overview | One rolled-up snapshot: events, active users, p95 and uptime | `GET /analytics/overview` |

<Callout title="Ingest from the app, read from the backend">
Tracking (`trackEvent`) is usually called from your running app, so a client
SDK sends it with the signed-in session and Applad attaches the `userId`
automatically. The rollups (counts, DAU, funnels) are read from trusted code
with an API key.
</Callout>

## Track an event

An event needs a `name`; everything else is optional context. Custom fields go
in `properties`.

<Tabs items={['JavaScript', 'Node.js', 'Python', 'cURL']}>
<Tab value="JavaScript">
```ts
await client.analytics.trackEvent('added_to_cart', {
  sku: 'APL-42',
  price: 1999,
});
```
</Tab>
<Tab value="Node.js">
```ts
await server.analytics.trackEvent('order_completed', { orderId: 'ord_1', total: 4999 });
```
</Tab>
<Tab value="Python">
```python
client.analytics.track_event("order_completed", {"orderId": "ord_1", "total": 4999})
```
</Tab>
<Tab value="cURL">
```bash
curl -X POST https://api.applad.io/v1/analytics/events \
  -H "x-applad-project: <projectId>" -H "x-applad-key: <apiKey>" \
  -H "Content-Type: application/json" \
  -d '{"event":"added_to_cart","properties":{"sku":"APL-42"},"userId":"user_123"}'
```
</Tab>
</Tabs>

Underlying route: `POST /v1/analytics/events`. Besides `event`, `userId` and
`properties`, an event can carry `sessionId`, `url`, `referrer`, `deviceType`,
`browser` and `country`. When `userId` is empty it is filled from the
authenticated caller. The stored event is returned with its `$id` and
`$createdAt`.

To send many at once, `POST /v1/analytics/events/batch` with an `events` array
inserts them in a single transaction and returns how many were processed.

## Read events back

`GET /v1/analytics/events` returns raw events, newest first, with filters:

| Query param | Filters by |
| --- | --- |
| `event` | exact event name |
| `userId` | a single user |
| `from`, `to` | a time window (RFC3339 timestamps) |
| `limit`, `offset` | pagination (default `limit` 100, max 1000) |

```bash
curl "https://api.applad.io/v1/analytics/events?event=added_to_cart&limit=50" \
  -H "x-applad-project: <projectId>" -H "x-applad-key: <apiKey>"
```

The response is `{ "total": n, "limit": ..., "offset": ..., "events": [...] }`.
The SDK `listEvents(params)` wraps this route.

## Counts over a window

`GET /v1/analytics/events/counts` groups events by
name over a time window and returns each event's total. The window defaults to
the last seven days; pass `from` and `to` as RFC3339 to change it.

```json
{
  "counts": {
    "page_view": 8123,
    "added_to_cart": 640,
    "order_completed": 210
  }
}
```

The SDK exposes this as `getStats(params)`.

## Live snapshot

`GET /v1/analytics/realtime` returns a lightweight snapshot of the last five
minutes: distinct active users, distinct active sessions, and the raw event
count. It is meant for a "right now" tile on a dashboard.

```json
{ "activeUsers": 37, "activeSessions": 41, "eventsLast5m": 512 }
```

The SDK method is `getRealtimeCount()`.

## Daily active users

`GET /v1/analytics/dau` returns one row per day with the count of distinct users
who fired any event that day, across the requested window.

```json
{ "data": [ { "date": "2026-07-20", "users": 611 }, { "date": "2026-07-21", "users": 640 } ] }
```

<Callout title="What the SDK covers">
The `analytics` service in every SDK covers the everyday surface —
`trackEvent`, `listEvents`, `getStats`, `getRealtimeCount`, `getOverview`,
plus the uptime and cron monitors and `cronCheckin`. Batch ingest and funnel
analysis are available over the `/v1/analytics` routes above.
</Callout>
