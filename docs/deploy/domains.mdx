title: Custom domains
description: "Serve a web target on a domain you own by adding it and verifying ownership over DNS."
---

A `web` target already answers on its `<name>.applad.dev` address. To serve it
on a domain you own, add the domain and verify ownership over DNS.

```bash
curl -X POST "$APPLAD/v1/deploy/targets/$TARGET/domains" \
  -H "x-applad-project: $PROJECT" -H "x-applad-key: $KEY" \
  -H "Content-Type: application/json" \
  -d '{"domain": "app.example.com"}'
```

The response carries a `verification` token and starts as `verified: false` with
`sslStatus: "pending"`. Add a TXT record containing the token, either on the
domain itself or on `_applad-verification.<domain>` (a CNAME containing the token
also works), then verify:

```bash
curl -X POST "$APPLAD/v1/deploy/targets/$TARGET/domains/$DOMAIN/verify" \
  -H "x-applad-project: $PROJECT" -H "x-applad-key: $KEY"
```

On success the domain flips to `verified: true` and `sslStatus: "active"`. List
a target's domains at `GET /v1/deploy/targets/{targetId}/domains`; the assigned
`.applad.dev` address is included there too, since it is the domain that serves
traffic by default.

## How TLS and DNS work

You do not request certificates or add a DNS record per site. A single wildcard
record covers every app subdomain (`*.applad.dev` points at the edge), and
certificates are issued on demand, per hostname, the first time a name is
requested. The edge only obtains a certificate for a name that belongs to a live
app: a subdomain currently claimed by a deploy target, or a verified custom
domain. A name that matches no live app gets no certificate, so the wildcard
record cannot be used to mint certificates for arbitrary hostnames.

A self-hosted instance follows the same model against whatever deploy domain it
is configured with. See [getting started](/getting-started) for bringing up the
stack.
