Most backends stop at build and deploy. Applad also runs **your project's own
tests**. You point it at a body of tests (a git repo or an upload), it builds an
image, runs it to completion in a container, and reads the JUnit XML report the
run leaves behind. From that one report Applad records every case, keeps its
history across runs, marks the ones that failed-then-passed as flaky, and stores
any screenshots or videos the run produced.

Because the interchange format is JUnit XML, Applad never has to know whether you
use Jest, pytest, `go test`, `flutter test`, or Playwright. You describe how your
suite runs, and the report says what happened.

<Callout title="This is an operator and CI task">
  Test configuration and runs are server-side work: you drive them with a
  **server API key** (`x-applad-key`), from CI or a trusted environment, not from
  end-user code. All routes live under `/v1/tests` (and `/v1/studio` for the
  recording studio). The 5 client/server SDKs do not wrap the Test module yet, so
  the examples below use the REST API directly and the console UI.
</Callout>

<Callout title="Runs need Docker">
  Runs execute on Applad's builds worker, which holds the Docker socket. A
  self-hosted install already runs this worker as part of `docker compose up`, so
  no extra setup is required. Test containers join the deploy network, so a
  browser suite can reach a deployed app by container name (see
  [Sites](/deploy/sites)).
</Callout>

## Four objects

The Test module is built from four objects. Keeping them separate is what lets
one suite check several environments and lets a known-flaky test stop blocking
deploys without being deleted.

| Object | What it is |
| --- | --- |
| **runner** | How tests execute: the image, the setup command, the test command, and where the JUnit report lands. A project usually has one or two. |
| **test** | One behaviour. Recorded flows create one directly; authored tests are discovered the first time a run reports them. Tagged, quarantinable, carries history. |
| **suite** | A selection of tests by tag, plus its triggers: on deploy, on a schedule. |
| **run** | A suite (or a whole runner) executed against a target, at a moment. |

The **target** belongs to the run, not the test, so one suite can check `main`
and a branch rather than being duplicated per environment.
