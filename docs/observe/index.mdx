Most backends stop at deploy. Observe is the stage after: once your app is
running in production, it tells you how it is actually doing. Errors, logs,
request performance, uptime, scheduled-job health, and alert rules all live
under a single `/v1/observe` API and share the same project scope as the rest
of Applad. You capture events from your app (or let Applad collect them for
you), then query them back or watch them in the console.

This is the piece a plain BaaS usually leaves you to bolt on with a separate
Sentry or an uptime service. Here it is part of the same project as your
[databases](/build/databases), [functions](/build/functions), and
[deployed sites](/deploy/sites), reachable with the same key.

<Callout title="Everything here is project-scoped">
Every route below lives under `/v1/observe` and requires the project header
`x-applad-project: <projectId>` plus authentication. Client SDKs send the
session bearer token after [login](/build/authentication); server code sends an API
key header `x-applad-key: <apiKey>`. Ingestion (capturing errors, logs, and
web vitals) is typically done from your running app, so most examples use the
client SDK.
</Callout>

## Setup

The examples use the Dart client SDK and raw `curl`. Configure a client once:

```dart
final client = Applad()
    .setEndpoint('https://api.applad.io/v1')
    .setProject('<projectId>');
// after client.auth.createEmailSession(...) the SDK sends the session token
```

For server-side or ad-hoc calls, set these and reuse them:

```bash
export APPLAD=https://api.applad.io
export PROJECT=<projectId>
export KEY=<apiKey>
```

## What Observe gives you

| Capability | What it does | Real endpoints |
|---|---|---|
| Error tracking | Capture exceptions, group them by fingerprint, triage (resolve / ignore / assign / prioritise), and read per-issue activity | `GET/POST /observe/errors`, `.../{errorId}` and status routes |
| Logs | Ship structured log lines with level, source, trace/span IDs, and metadata; query them back | `GET/POST /observe/logs` |
| Performance | Per-endpoint latency percentiles (p50/p75/p95/p99), throughput, error rate, and browser web vitals | `GET/POST /observe/performance`, `POST /observe/performance/vitals` |
| Uptime monitors | Applad polls a URL on a schedule and records status, latency, and uptime percentage | `GET/POST/DELETE /observe/uptime` |
| Cron monitors | Scheduled jobs check in when they run; the monitor records duration and history | `GET/POST/DELETE /observe/crons`, `.../{monitorId}/checkin` |
| Alert rules | Define threshold rules on a metric (error rate, latency, and so on) and list open incidents | `GET/POST/DELETE /observe/alerts` |
| Overview | A single rolled-up snapshot: errors today, logs last hour, p95, uptime | `GET /observe/overview` |
| Releases | Record a release version with its commits and read release-level issue counts | `GET/POST /observe/releases` |
| Session replays | Store and read back session recordings (events, network, console) | `GET/POST /observe/replays` |

The sections below show how to send and query each. The linked pages go deeper
on the ones with the most surface area.

## How the pieces connect

Tag your errors and logs with the same `release` and `environment` you record
in Releases, and one version's issues line up across all three. Uptime and
cron monitors run independently of your app and keep reporting even when it is
down. The Overview endpoint reads across errors, logs, performance, and uptime,
so it is the natural thing to put on a project dashboard.

For self-hosters: Observe needs no extra services. Error, log, performance, and
replay data live in PostgreSQL alongside everything else, and the uptime worker
and performance collector start with the API. See [self-hosting](/self-hosting)
for the base stack.
