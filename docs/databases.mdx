---
title: Databases
description: Tables, rows, queries, and the permission model that decides who can read and write each row.
---

An Applad database is real PostgreSQL. You define **tables** with typed
**columns**, write **rows**, and query them through a fluent builder. Access is
governed by permissions enforced in the database itself, so a rule you set is a
rule the database keeps, not one your client is trusted to honour.

## Tables, columns and rows

```dart
final db = client.databases;

await db.createDatabase(name: 'app', databaseId: 'app');
await db.createTable(
  databaseId: 'app', tableId: 'messages', name: 'messages',
  permissions: ['create("users")'],   // who may insert
  documentSecurity: true,             // each row also carries its own permissions
);
await db.createStringColumn(databaseId: 'app', tableId: 'messages', key: 'body', size: 8000, required_: true);

await db.createRow(
  databaseId: 'app', tableId: 'messages',
  data: {'body': 'hello'},
  permissions: ['read("team:$teamId")'],
);
```

Defining tables and columns is an operator task — do it once at setup (from the
console, a migration, or a script using an API key), not from end-user code.

## Querying

`from(...)` builds a query; filters, ordering and pagination chain onto it:

```dart
final result = await db
    .from('app', 'messages')
    .equal('channel_id', channelId)
    .orderAsc('created_at')
    .limit(50)
    .get();

for (final row in result.rows) {
  print(row['body']);   // custom columns sit at the top level of the row
}
```

Every row also carries system fields: `$id`, `$createdAt`, `$updatedAt` and
`$permissions`.

## Permissions and row-level security

Permissions are strings of the form `action("role")`. The actions are `read`,
`create`, `update` and `delete` (`write` is shorthand for update + delete). The
roles are:

| Role | Matches |
| --- | --- |
| `any` | everyone, signed in or not |
| `users` | any signed-in user |
| `user:<id>` | one specific user |
| `team:<id>` | every member of a team |
| `team:<id>/<role>` | members of a team who hold a role |

Roles are resolved **server-side from the caller's own identity and team
memberships** on every request. A client never sends its own roles; if it could,
it could grant itself anything.

### Two layers: table and document

A permission set on the **table** applies to every row in it — good for "any
signed-in user may read this table". Turn on **document security**
(`documentSecurity: true`) and each row *also* carries its own permissions:
access is granted when the table grants it **or** the row grants it. This is what
lets one shared table hold data that different groups see different slices of.

```dart
// This message is readable by the channel's members, and editable/deletable
// only by its author.
await db.createRow(
  databaseId: 'app', tableId: 'messages',
  data: {'channel_id': channelId, 'body': 'hello'},
  permissions: [
    'read("team:$channelId")',
    'update("user:$myUserId")',
    'delete("user:$myUserId")',
  ],
);
```

With that in place a member of the channel's team sees the message, a non-member
sees nothing (not even in a list query), and only the author can change or remove
it. The enforcement is PostgreSQL row-level security, so it holds for the query
builder, raw SQL and the realtime read path alike.

<Callout title="Fails closed">
  A row with no permission that grants a caller `read` is simply invisible to
  them — list queries skip it rather than erroring. If you create a
  document-security table and see no rows, check that each row grants `read` to a
  role the caller actually holds.
</Callout>

### Owner column

If a table has an owner column (a column naming the user who owns each row),
that user always has full access to their own rows, without you setting per-row
permissions for them.
